Chapter 6

The KV cache: remembering without re-reading

Look back at Chapter 5's decode loop: after picking " Paris", the model has to run again to guess the next token. Naively, that means re-processing the entire sentence plus "Paris" through all 12 layers from scratch — repeating work it already did a moment ago. This chapter is about the fix, and exactly what it does and doesn't remember.

The fix is called a KV cache, short for "key/value cache" — a direct reference to the Key and Value roles from Chapter 3's attention spotlight. The engine keeps a running notebook of every earlier token's Key and Value, per layer, so each new token only ever needs to be processed once.

Why only Key and Value — not Query

This is the detail people usually skip, and it's worth getting precisely right, because it explains the name. Recall the library-desk analogy: your Query is the question you bring right now; a book's Key is its spine label; a book's Value is what's actually inside it. A token's Query is only ever needed once — at the exact moment it's the newest word asking "what matters to me?" Once that moment passes, its Query is never consulted again. But that same token's Key and Value get re-checked by every single word that comes after it, for the rest of the conversation. So Query is used-and-discarded; Key and Value are the only things worth holding onto — hence, K/V cache, not KVQ cache.

Tracing it through our real example

Prefill processes all 6 prompt tokens at once and stores a Key and Value for each of them — the cache now holds 6 entries per layer. The model picks " Paris" (id 6342). Decode step 1 feeds only "Paris" back in: it computes Paris's Key and Value and appends them — the cache now holds 7 entries — while Paris's Query checks itself against all 7 (the 6 old entries plus its own) to guess the next token, "." (id 13). Decode step 2 feeds in just ".", growing the cache to 8 entries, and predicts the stop token. Notice: every step computes exactly one new Key/Value pair and reuses everything before it.

What's actually sitting in the notebook

"A Key and Value per token" is short for something more specific: this project stores one Key vector and one Value vector per attention head, per layer, per token. GPT-2 Small has 12 layers and 12 heads per layer, so a single token's entry isn't one pair of numbers — it's 144 small pairs (12 × 12), each 64 numbers long (GPT-2's head size). That adds up fast, and it's why the cache is measured in real memory, not just an abstract "notebook":

A real, if small, number

12 layers × 12 heads × 64 numbers-per-head = 9,216 numbers for Keys, and another 9,216 for Values — 18,432 numbers per token. This project stores every number as a 4-byte value, so that's roughly 72 KB of cache for a single token, on a genuinely small, 1990s-arcade-game-sized model. Scale up to a modern model with more layers, more heads, and a bigger head size, and per-token cache cost climbs into the hundreds of kilobytes — multiplied by every token in every active conversation, simultaneously. This is why cache size, not raw model cleverness, is often the thing that actually limits how long a conversation or how many simultaneous users an engine can afford.

Analogy

It's less like one notebook and more like 144 separate index-card trays (12 layers × 12 spotlights each) — and every single token you've said or the model has said gets a new card filed into every one of those 144 trays. The trays never shrink. They only ever gain more cards, for as long as the conversation continues.

That "never shrink" property is exactly what Chapter 7's context window is a limit on, and exactly the problem Chapter 8's Mamba2 layers solve in a completely different way — worth keeping in mind as you read on.

Under the hood The cache itself is KVCache in purego/tensor/kv_cache.go — one Keys[layer] and Values[layer] tensor per layer, shaped [batch, num_heads, seq_len, head_dim]. It's read and appended to inside MultiHeadAttention.ForwardWithCache() in purego/tensor/attention.go on every forward pass.
