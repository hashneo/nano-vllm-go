Chapter 7

The engine room: serving many people at once

Chapter 6 was about one conversation avoiding wasted work. This chapter is about what happens when hundreds of conversations want the model's attention at the same time — a whole separate set of problems that have nothing to do with how smart the model is.

Analogy

Think of the model as a brilliant chef, and the inference engine as the kitchen manager. The chef's skill matters, obviously — but so does whether the kitchen can handle six tables' orders at once without everyone waiting for everyone else, and whether the pantry has room for every table's ingredients simultaneously. Those are the kitchen manager's problems, not the chef's. This chapter is about the kitchen.

Problem 1: the notebook isn't infinite — the "context window"

Chapter 6's KV cache notebook has to live somewhere in the computer's memory, and memory is finite. This is exactly what a model's advertised context window (like "128,000 tokens") really refers to: it's the maximum size that notebook is allowed to grow to. Once your conversation's tokens — question and answer combined — hit that ceiling, something has to give: older parts get dropped, or the engine refuses to go further.

Here's a fact worth sitting with: the context window is decided by both the model and the engine, not just one or the other. The model sets an upper bound — GPT-2 was built with a seating chart (Chapter 2) that simply has no chair past position 1,024, so it cannot go further no matter what. But even for models with a much bigger upper bound, the engine running them has to actually set aside enough memory for that notebook — and on limited hardware, the engine might cap it far below what the model is theoretically capable of, simply because there isn't room.

Problem 2: serving more than one person at once

Real deployments rarely serve one question at a time — dozens of people are asking things simultaneously. Running them one-at-a-time, start to finish, would mean everyone in line waits for everyone ahead of them, even though most of the actual work (loading the model, setting up computation) could be shared.

Analogy

A good kitchen doesn't cook one full order start-to-finish before glancing at the next ticket — it interleaves them, starting a new table's order the moment there's a free burner. The engine's scheduler does the same thing: it continuously mixes together bits of work from many people's conversations, called continuous batching, so hardware never sits idle waiting for one particular person's next word.

And rather than reserving one giant fixed notebook per person (wasteful — most conversations are short), the notebook is carved into small reusable pages, called blocks, that get handed out and returned as needed. If two different people start their conversation with the exact same opening text, the engine can even notice and let them share the same already-filled-in pages — called prefix caching — instead of filling in two identical notebooks separately.

The real name for this trick

This block-and-page approach to KV cache memory has a specific name in the research world: PagedAttention, introduced by the vLLM project (a real, widely-used, high-performance inference engine — the project you're reading right now, nano-vllm-go, is a small, from-scratch, educational homage to it, hence the name). The core idea, borrowed directly from how operating systems page virtual memory, is exactly what you just read: stop treating each conversation's cache as one contiguous block, split it into fixed-size pages instead, and let a lookup table (a block table) map each conversation to whichever pages it's currently using — wherever they happen to sit in memory.

Recap

The model decides what a good answer looks like. The engine decides how much memory that costs, how many people can be served at once, and how long a conversation is actually allowed to be on this hardware right now. Both matter — a brilliant model with a poorly built engine around it is still going to feel slow and expensive.

Under the hood The block-based notebook and prefix-caching hashing are implemented in nanovllm/block_manager.go. The scheduler/continuous batching logic is in nanovllm/scheduler.go and nanovllm/llm_engine.go. The context-window setting itself is Config.MaxModelLen in nanovllm/config.go, separate from the model's own trained limit (ModelConfig.MaxSeqLen in purego/tensor/config.go).
